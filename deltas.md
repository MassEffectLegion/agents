# Дельты (delta1 / delta2 / delta3) — сабагенты-исполнители

> Детальный файл о сабагентах-исполнителях. Начните с [README.md](README.md) — общий
> обзор и глоссарий. Здесь — роли, профили моделей и устройство дельт.
> Секреты — плейсхолдеры «см. vault / agent_settings (БД)». IP/порты — в `agent_settings`.

## 1. Роль

Дельты — **сабагенты**: те же longlive-циклы, что и у основных агентов (запуск → работа
→ рестарт → снова), но с профилем **ИСПОЛНИТЕЛЯ**. Они делают рутинную и быструю работу
по поручению и **эскалируют** сложные/деструктивные решения оркестратору (почта /
канал с человеком), а не принимают их сами. Read-only по чужому коду.

Все три — тот же каркас longlive (`main.py` + `core/` + `tools/`, как у основных
агентов), отличаются моделью, профилем и набором специализированных инструментов.

```
оркестратор (сеньор)
      │  задачи (очередь задач / почта)
      │
 ┌────┴─────────────┬──────────────────┐
delta1             delta2            delta3
инфраструктура    OCR/зрение         быстрый текстовый анализ
+ OCR скриншотов  (документы,       (черновики, сканер,
(LLM-сервера/GPU/  изображения)      разведка)
VPN/диск)
      │  эскалации (почта / канал с человеком)
      └──────────────┬──────────────┘
                  оркестратор принимает решение
```

## 2. Общие правила (task.txt каждой дельты)

- Долгоживущие циклы: запуск → работа → рестарт → снова; **без** «finish» — до явной
  остановки человеком.
- Восстановление «я» — последний чекпоинт (`analyst_daemon_queue`,
  `request_payload->>'agent'='deltaN'`).
- Каждый цикл: (1) восстановить «я» + прочитать входящие (канал с человеком / очередь
  задач); (2) проверить живость напарников (`lives`); (3) вести свой контур по
  чекпоинтам; (4) оставить свежий чекпоинт в конце цикла.
- **САБ-агент**: сложные/деструктивные решения — ЭСКАЛАЦИЯ оркестратору, не действовать
  самому.
- Read-only по чужому коду. Не трогать общие LLM/RAG-серверы и других агентов
  (адреса/порты — в `agent_settings`).
- Память — PostgreSQL, те же таблицы, что у основных агентов (см. [README.md](README.md) §4).

## 3. Профили моделей

| Агент | Модель (GGUF) | Размещение | Окно | Профиль |
|---|---|---|---|---|
| **delta1** | Ternary-Bonsai2-27B-Q2_0 | GPU0 (слот из agent_settings) | 90k | **ИНФРАСТРУКТУРА** Linux-хоста (LLM-сервера/RAG/VPN/диск/GPU) + зрение (mmproj) + reasoning + OCR скриншотов |
| **delta2** | gemma-4-E4B-it-Q4_0 | GPU1 (слот из agent_settings) | 64k | **OCR/зрение**: скриншоты, документы, изображения; быстрый и компактный, лёгкие сводки |
| **delta3** | Spark-X2.6-4B-Q8_0 | GPU0+GPU1 (layer-split) | 45k | **Быстрый текстовый анализ** (~80 tok/s): черновики, сканер, разведка; без зрения |

Идея профиля: одна большая модель (27B) — для «умной» инфраструктурной работы и чтения
скриншотов; две маленькие (4B) — для массовой быстрой работы (OCR-поток, черновики),
которая не должна ждать большого окна.

## 4. Каталог

Аналогичен основному агенту: `<workdir>/main_workdir/deltaN/`
(`main.py`, `core/`, `tools/`, `workspace/`, `logs/`, `progress/`, `task.txt`,
`longlive_plan_*.md`, `run_deltaN.bat`, `runtime_*.json`, `sleep_watchdog_deltaN.py`).
Различия:

- `task.txt` — профиль дельты (модель + роль) — единственный источник для промпта.
- `core/` — тот же longlive-набор модулей (см. [harness_report.md](harness_report.md) §2 — канон).
- `tools/` — общий longlive-набор + СПЕЦИАЛИЗИРОВАННЫЕ:
  - три инструмента к API оператора (адрес — в `agent_settings`): `db_api_health`
    (health), `db_api_query` (read-only `/query`) и `db_api_write` (запись через
    СОБСТВЕННЫЙ API оператора — dogfood, НЕ raw-запись в БД; fallback на
    psycopg2 при недоступности API). Честно: «read-only по умолчанию» — это
    политика SQL-инструментов, а `db_api_write` — осознанное исключение
    (собственная запись агента через API).
  - `web_search` — веб-поиск (профиль delta3 «разведка»);
  - декодеры TG-сообщений;
  - одноразовые recon-скрипы (разведка окружения, документы, пути репозиториев);
  - стандартный набор: SQL, файлы, запуск Python, чекпоинты, controlled restart, RAG
    (поиск + запись), батч-анализ логов/файлов через LLM, SSH, SFTP, TG-роли, path-guard.

## 5. Связь с оркестратором

- **Оркестратор-сеньор** — координатор: ставит задачи (очередь задач / почта), принимает
  эскалации, ревьюит результаты.
- **Меж-агентная почта** (`agent_mailbox`) — канал delta→оркестратор (эскалации, статусы).
- **Канал с человеком** — дельты могут писать человеку (через оркестратора или прямые
  запросы со статусом ожидания ответа).
- **lives** — живость каждой дельты видна всем (`last_heartbeat_at`, `restart_count`).
- **agent_sleeps** — спячка (wake_at / need_work) — как у всех longlive-агентов.

## 6. Безопасность

- NEVER-REVEAL (секреты/токены/ключи/внутренние IP+порты БД) — как у основных агентов.
- SQL: read-only по умолчанию (`allow_write=False`); запись — только в своём контуре
  и по явному разрешению (исключение — `db_api_write`, см. §4).
- Path-guard: только разрешённые каталоги (свой workspace, общие каталоги).
- Не трогать чужих агентов и общие LLM/RAG-серверы (read-only диагностика — можно).

## 7. Запуск

- Скрипт запуска (`run_deltaN.bat`) — старт longlive-цикла.
- Модель: любой OpenAI-совместимый сервер (llama-server) с GGUF-моделью; слот GPU и порт
  — из `agent_settings` (у каждого агента свой слот, чтобы не конфликтовать).
- БД: PostgreSQL, креды — в `agent_settings` / vault.
