## 1. ОБЩИЙ ВИД И РОЛИ

Система: кластер долгоживущих автономных LLM-агентов (локальные GGUF-модели через
llama.cpp, OpenAI-совместимый API). Каждый агент — бесконечный цикл `запуск → работа
(tool-calls) → рестарт (сброс контекста) → снова`, до явной остановки человеком.
Память между рестартами — PostgreSQL + файлы (контекст LLM сбрасывается каждый рестарт).
Мотивация «почему так, а не фреймворк» — [README.md](README.md) §1.

| Агент | Роль | Ключевое |
|---|---|---|
| **gemma** | АНАЛИТИК | аналитика, RAG-память, отчёты, owner-координация в цепочках, документация |
| **alfa** | ОРКЕСТРАТОР | инфраструктурный контур, VPN, дельты, gitlab/деплой, TG-валидатор (роли чатов owner/project/guest; для project/guest — только рекомендации) |
| **bravo** | ОПЕРАТОР | TG-мост (tg_bridge), деплой, инфраструктура, ротация |
| **delta1/2/3** | сабагенты-исполнители | рутинная работа, эскалация сложных решений alfa-сеньору |
| **omega** | резерв | работает БЕЗ PostgreSQL (SQLite + файлы), failover LLM |
| **lima** | лёгкие агенты | idle_sleep, короткие ответы (приёмник TG-роутинга guest) |

Вспомогательные: фоновые сабагенты-инструменты (RAG-инжестор, vision-OCR),
read-only HTTP API к БД, watchdog-демоны спячки.

## 2. ЦИКЛ И ЯДРО (общий каркас, одинаков у alfa/bravo/gemma/deltas)

```
bootstrap:
  AgentCheckpoint(PG)        # «я» = последний чекпоинт analyst_daemon_queue
  report_start(lives)        # якорь живости (heartbeat) + watchdog
  non-fatal демоны: llm_lives_ensure, startup_archive, sleep_watch, (фоновая зависимость)
  tools = get_tools(); LoopGuard
ЦИКЛ:
  report_alive(lives)
  fetch_llama_config (llama-server, слот agent_slot) → ChatOpenAI.bind_tools
  ContextBudget (n_ctx, max_tokens, schemas) — tokenize API + fallback UTF-8
  prompt = первичный промт + ПАМЯТЬ ИЗ БД (чекпоинт, входящие, задачи) — вшивается автоматически
  tool-loop до no_tool_response_limit / budget
конец цикла:
  ~80% контекста → save_progress (чекпоинт PG + progress/*.json) → request_restart
  controlled restart: чистый выход ПОСЛЕ шага, процесс поднимается заново (сброс контекста)
  нет задач → sleep (--sleep Nm --reason) → agent_sleeps → sleep-guard останавливает
  sleep_watch (каждые 5 мин, FOR UPDATE) поднимает в wake_at или при need_work=true
```

Ключевые механизмы:

- **ContextBudget** — лимит окна (по умолч. 95%); при исчерпании — controlled restart,
  причина пишется в чекпоинт.
- **K1 pre-flight** — валидация JSON tool-call ДО execute; ошибка → ToolMessage с
  требованием исправить (1 авто-ретрай), а не 500/рестарт.
- **F3 correction** — на «Failed to parse tool call arguments» — короткая corrective-
  HumanMessage (разбей большой write на чанки), 3 попытки, откат на финальном неудаче.
- **Output bounding** — результат инструмента > лимита → полный вывод в файл
  `logs/tool_outputs/<uuid>.txt`, в промпт — отсечка + путь.
- **BaseException-safe** — SystemExit/KeyboardInterrupt из инструмента не убивают агента.

**Граница K1 vs F3 (почему оба).** K1 — валидация схемы аргументов tool-call на стороне
клиента ДО вызова инструмента: невалидный JSON не уходит на сервер, модель получает
ToolMessage «исправь» (1 авто-ретрай). F3 — срабатывает позже, когда сам llama-server
отдаёт 500 «Failed to parse tool call arguments» уже при парсинге сгенерированного
tool-call (до возврата управления в наш код): короткая corrective-сообщение «разбей
большой write на чанки», 3 попытки. K1 ловит опечатку клиента, F3 — сбой генерации на
сервере; они не дублируют, а покрывают два разных слоя.

**Две границы, три сценария** (floor и плановый совпадают по умолчанию — 80%,
разводятся только настройкой):

- **Граница 1 — floor (нижний guard)** = `controlled_restart_threshold`, деф. **80%**,
  валидация 50–94 (факт в `agent_settings` = 80; 60% — нет, не было). Ниже floor
  `request_restart` **отказывается**: «рестартовать почти пустой цикл бессмысленно»
  + нужно ≥ `min_tool_calls_for_controlled_restart` (3) tool-вызовов. Это защита от
  «побега в рестарт»: модель не может сбросить контекст, когда цикла ещё почти нет.
- **Граница 2 — hard (лимит окна)** = `context_usage_percent`, **95%**. Достижение =
  controlled restart по безопасности (safety net).
- **Плановый (warn/controlled)** — по умолчанию совпадает с floor (80%): NOTE
  «контекст выше порога» → завершённый шаг = `save_progress` + `request_restart`;
  шаг критичный и короткий → доделать и остановиться. Лимит: ≤ N (2)
  controlled-рестарта за окно (30 мин) + 1 за цикл.

**Три сценария:** (1) ctx < floor — рестарт ОТКЛОНЁН, цикл продолжается;
(2) floor ≤ ctx < hard — агент сам поднимает плановый controlled-restart;
(3) ctx ≥ hard — hard-restart как страховка. Агент никогда не «допирается до края».

**Ветвление по типу задачи.** Сложная задача (много tool-calls, большие ответы) — агент
поднимает плановый рестарт у нижнего/среднего порога, чтобы не упереться в 95%. Рутина
(короткие ответы, сон) — цикл идёт до 95% или в спячку. Агент никогда не «допирается
до края» окна: либо чистый controlled-restart, либо сон, либо hard-limit как страховка.

Каталог агента `<workdir>/main_workdir/<agent>/`:

- `main.py` — ядро цикла;
- `core/` — ~23 модуля (config, bootstrap/system prompt yaml, longlive_memory,
  llama_runtime, db_access/db_failover, sql_safety, loop_guard, token_tracker,
  tg_readonly_guard, rerank_client, lives_report, startup_archive, sleep, ...);
- `tools/` — ЭТАЛОННЫЕ инструменты: SQL (запрос/вставка/схема), файлы, запуск Python,
  SSH/SFTP, RAG (поиск + запись), чекпоинты, controlled restart, сон, почта,
  батч-анализ логов/файлов через LLM, TG-роли, path-guard, ...;
- `workspace/tools/<task_id>/` — одноразовые скрипты (реестр `tools_registry`);
- `archive/`, `logs/` (+ `tool_outputs/`), `progress/` (JSON-чекпоинты).
- **ИЕРАРХИЯ**: `core/` и `tools/` (эталон) пишутся ТОЛЬКО через ревью человека;
  `workspace/` — черновики агента; полезный workspace-инструмент после задачи
  предлагается «поднять в core».

> **Счётчики «модулей/инструментов» отличаются по агенту** (у каждого свой набор под
> роль). Для gemma на 11.11: `core/` 23 файла (21 `.py` + 2 prompt-`.yaml`), `tools/`
> 27. Не сравнивайте числа между агентами — это разные роли, не разные версии.

### Протокол цепочек задач v2.1 (согласован человеком)

- Задания видят ВСЕ агенты. **reader-merge**: прочитавший ставит свой ключ в
  `task_notes.readers` (идемпотентно).
- **Claim**: первый увидевший ЗАБИРАЕТ атомарно: `UPDATE ... SET claimed_by=<me>,
  status='in_progress' WHERE claimed_by IS NULL AND status IN ('new','open')` → owner.
- **Pipeline**: new → analyze → plan → execute → done (двигает только owner).
- **ANALYZE**: owner → `task_analyze` (analyzed, сводка 3-5 строк + файл анализа);
  остальные — свой файл + 1 строка в `task_notes.reviews` (verdict/file/ts).
- **PLAN**: owner читает ВСЕ reviews → `task_plans` (шаги, prompt_agents).
  >1 агента в шаге = ПАРАЛЛЕЛЬНО (каждый пишет СВОЙ файл — conflict-free).
- **EXECUTE**: owner шага фиксирует `file_short_result` («agentA:done,agentB:done» +
  результат); шаг done, когда ВСЕ имена из prompt_agents отмечены. Переходы —
  `agent_coordination` (step_start/step_done).
- **Маленькая задача (1 шаг)**: analyze пропускается — сразу 1 шаг в task_plans.
- **Z3**: owner молчит 30 мин → второй НЕ забирает задачу: письмо + вопрос человеку
  (переназначение — только человек).
- **DONE**: все шаги → task_analyze.done + очередь задач done + единый отчёт человеку.

## 4. TG-КОНТУР (мост — bravo)

**IN-путь** (TG → БД): поллер в docker-контейнере на Linux-хосте — Telegram Bot API
`getUpdates` → дедупликация по `tg_msg_id` → INSERT `tg_message_queue` (status='new') +
вложения (download → таблица вложений: md5, size, путь; текст дополняется
`[att:<id>]`, идемпотентно). Lock `{pid,ts}` с reclaim-логикой (защита от crash-loop:
mёртвый lock старше порога забирается).

**OUT-путь** (БД → TG): outbox-поллер — отчёты/ответы → TG-чат; HR-зеркало —
двунаправленное зеркало канала с человеком (двойная доставка с дедупом).

**Валидация** (назначенный агент — валидатор, чек-лист):
- a) **DANGER** (danger_patterns из настроек: SQL-уничтожение, удаление файлов, выдача
  секретов, remote-exec) → `denied`;
- b) **ВАЛИДНОСТЬ** (понятно, в рамках контуров; пустое/спам) → `quarantined`;
- c) **SCOPE**: chat_id сверяется со списком чатов и ролей (owner|project|guest);
  неизвестный чат → `denied scope:unknown-chat`;
- d) **WRITE-ИНТЕНТ**: role guest/project = РЕКОМЕНДАЦИЯ, НЕ КОМАНДА → write-запрет
  (ответ = разъяснение + вариант без исполнения).
- Финальные статусы: `denied | clean | routed | quarantined` (+ validate_note, routed_to,
  handled_at). Валидатор имеет write-доступ только к колонкам статуса очереди.
- **NEVER-REVEAL**: секреты/токены/внутренние IP+порты БД; запрос на секрет →
  quarantined + эскалация человеку.

**ПЕРЕКЛАДЧИК** (роутинг, bravo): читает status='new' → роутинг по правилам ролей →
атомарно status='routed' + routed_to. Маршруты: owner/project → основной агент,
guest → лёгкий агент. Запуск ручной (--once/--status/--dry-run), lock {pid,ts}.
НЕ валидирует и НЕ создаёт задачи — это зона валидатора/агентов.

**ГРАБЛЯ (зафиксирована):** в БД ДВЕ схемы — живая `public` (читают поллеры) и зеркало
`agents_main`. TG-таблицы квалифицировать `public.*`, иначе запросы молча уходят в
зеркало. Перманентный фикс — в самом инструменте SQL (автоквалификация).

## 5. ДЕЛЬТЫ (delta1/2/3) и OMEGA

**Дельты** — сабагенты-исполнители на том же каркасе longlive; профиль: рутинная/быстрая
работа, ЭСКАЛАЦИЯ сложных/деструктивных решений alfa-сеньору (почта/канал с человеком),

Профили моделей и инструменты — [deltas.md](deltas.md).

**OMEGA** — резервный агент **БЕЗ PostgreSQL**: порируемый Python (runtime + vendor),
установка/интернет не нужны; SQLite-память (в т.ч. свои настройки), файловый чекпоинт,
longlive main.py. Две LLM (dense + MoE) — параллельный анализ поручения+памяти на
старте цикла, failover между серверами, слот-чистка. boot/manage/recovery/install_offline.
Работает ВМЕСТО остановленных основных агентов на тех же слотах.

## 6. RAG-СТЕК (память между рестартами, не в контексте)

- **Вектор**: BGE-M3 (Q8_0, ~566M, 1024d, ctx 8192) — llama-server на GPU-хосте
  (адрес в agent_settings/реестре), systemd-юнит. Мигрирован на GPU-хост
  (предыдущее размещение — мёртво).
- **Скорость**: эмбеддинг ~0.04–1 с (GPU; прежнее CPU-ограничение снято).
- **Хранилище**: pgvector, 1 вектор на карточку .md; карточки живут в общем каталоге
  (источник для записи).
- **Поиск**: косинус (min_score 0.6-0.7, top_k ≤ 5, теги-фильтр) + **реранкер**
  (bge-reranker-v2-m3; при сбое — vector-only fallback с пометкой в выводе).
- **In-place update** (без дублей): исправить .md → новый эмбеддинг → UPDATE по id.
- **Инжест**: фоновый суб-агент сам выводит тело карточки из файла-источника (обход
  лимита компактной модели на длинный JSON); основной агент делает запись вектора.
- **ДИСЦИПЛИНА**: карточка — ПОСЛЕ каждого инцидента/решения/нетривиального факта
  (2-3+ за цикл); устаревшее помечать `SUPERSEDED`/`[УСТАРЕЛО]` со ссылкой на
  актуальную карточку (иначе поиск возвращает мёртвые факты).

## 7. КЕЙС: «ОДНО TG-СООБЩЕНИЕ → ДВЕ ЗАДАЧИ» (root-cause)

**Ситуация.** Человек написал в Telegram одну фразу. Через ~20 минут в очереди задач —
две задачи с одинаковым содержанием.

**Факты (по журналам БД).**
- TG-поллер записал сообщение ОДНОЙ строкой — дедуп на уровне сообщений сработал
  (повторов строки в очереди нет).
- Через ~15 мин: валидатор пометил сообщение «routed, задача создана».
- Ещё через ~30 с: агент A (через роль валидатора) вставил задачу.
- Ещё через ~1 мин: агент B (в своём цикле, независимо) вставил ту же задачу.

**Коренная причина:** отсутствует дедупликация на уровне СОЗДАНИЯ задач.
Дедуп есть на уровне сообщений (поллер), но создание задачи из TG-сообщения делают
самостоятельно ДОЛГОЖИВУЩИЕ агенты в своих циклах: чтение очереди → «это новая задача»
→ INSERT. Два агента в перекрывающихся циклах независимо увидели одно сообщение — и
каждый сам вставил задачу. Перед INSERT никто не проверял, не создана ли уже задача из
этого источника; идемпотентного ключа/UNIQUE-ограничения в таблице не было — оба INSERT
прошли. Пометка «routed» не предотвращает: роутинг и создание задачи — разные
механизмы, а «routed»-метка не блокирует повторную обработку другим агентом
(чтение очереди — без блокировок).

**Фиксы.**
1. **Единый task-intake**: задачу из TG создаёт ОДИН компонент в той же атомарной
   транзакции, что и пометка «сообщение обработано» (INSERT ... ON CONFLICT DO NOTHING
   + UPDATE status='routed' WHERE status='new' в одной транзакции).
2. **Идемпотентный ключ**: `task_notes.source='tg:<chat_id>:<msg_id>'` + partial unique
   index по этому полю → второй INSERT гарантированно падает.
3. **Pre-flight перед INSERT**: SELECT по source; если задача уже есть — не создавать,
   а стать «читателем» существующей (reader-merge).
4. Каноническая метка «задача создана» — в записке валидатора (валидатор/роутер =
   единственный создатель).


Схема фикса (атомарно, в одной транзакции):

```sql
-- Идемпотентный ключ: partial unique index по источнику TG
CREATE UNIQUE INDEX CONCURRENTLY human_task_queue_tg_source_uniq
  ON human_task_queue ((task_notes->>'source'))
  WHERE task_notes->>'source' LIKE 'tg:%';

BEGIN;
INSERT INTO human_task_queue (task, task_notes)
VALUES ($1, jsonb_build_object('source', 'tg:' || $2 || ':' || $3))
ON CONFLICT (human_task_queue_tg_source_uniq) DO NOTHING;
UPDATE tg_message_queue SET status='routed', routed_to=$4
WHERE tg_msg_id=$3 AND status='new';
COMMIT;
```


**Обобщение:** в распределённой системе «кто-то уже сделал» проверяется на уровне
**сущности** (задача), а не только источника (сообщение). Повторения после фикса 2
невозможны по построению.

## 8. БЕЗОПАСНОСТЬ

- В MD — НИКАКИХ кредов/ключей/IP+портов БД: плейсхолдеры «см. vault / agent_settings

- Vault (боевой контур): KV-маунты секретов, read-only политики, read-токены;
  секреты из RAG-карточек мигрируются в vault.
- Path-guard, SQL read-only-политики, K1-валидация, never-reveal — см.
  [README.md](README.md) §5.

**Модель угроз (честно: от чего защищаемся и от чего НЕТ).**

| Защищаемся | Как |
|---|---|
| Prompt injection через TG | danger_patterns (SQL-уничтожение, удаление файлов, выдача секретов, remote-exec) → `denied`; scope-контроль (неизвестный чат → denied); guest/project — write-запрет (только рекомендации) |
| Деструктивный SQL от модели | K1 pre-flight (схема аргументов ДО execute), SQL read-only-политики, path-guard |
| Утечка секретов в отчёты/RAG | NEVER-REVEAL, плейсхолдеры в MD, grep-аудит перед публикацией, секреты → vault |
| Самомодификация ядра | `core/`/`tools/` меняются ТОЛЬКО через ревью человека; agent пишет в `workspace/` |
| Path traversal | единый path-guard (allowed dirs из settings, refresh 30 с) |

| **НЕ защищаемся** (честно) | Почему |
|---|---|
| Скомпрометированный хост (Windows/Linux) | если хост скомпрометирован — весь контур (ключи, БД, vault) под угрозой; это зона классической безопасности, не агентов |
| Злонамеренные веса модели (poisoned GGUF) | локальные модели, но если weights подменены/отравлены — agent может «улучшить» себя; защита = только доверенный источник весов + ревью |

## 10. ОГРАНИЧЕНИЯ (честно: что работает плохо / не решили)

- **Polling БД вместо событий.** Агенты читают очереди (`human_task_queue`,
  `tg_message_queue`, `agent_mailbox`) по таймеру/в цикле, а не по событию. Латентность
  = до интервала цикла + лишняя нагрузка на PostgreSQL. Нет pub/sub/событийного триггера.
- **Оценка контекста приблизительная.** ContextBudget считает токены через tokenize API
  llama-server + UTF-8 fallback (если API недоступен). Это оценка, не точный подсчёт;
  token_tracker держит **пиковое** значение, а не среднее.
- **Основной контур привязан к Windows.** Каталоги агентов, запуск циклов (.bat),
  общие каталоги — на Windows-хосте. Linux-хост — сервисы (LLM/BGE/MinIO/TG), но НЕ
  каталоги агентов и НЕ БД (БД — на отдельном Windows-хосте). Перенос на чистый Linux
  не завершён.
- **Нет distributed tracing.** Нет единого trace-id насквозь (TG → валидатор → агент →
  LLM → БД). Отладка — по журналам, артефактам save_progress, `agent_coordination`, а не
  по трейсам.
- **3 основных агента — потолок координации.** Больше агентов = боль координации, а не
  скорость (см. антипаттерны [README.md](README.md) §6.2). Это осознанное ограничение.
- **RAG — потеря контекста между рестартами, но не «понимание».** Поиск по векторам
  возвращает карточки, а не «вспомнил»; агент должен сам решить, что актуально
  (устранимо только дисциплиной SUPERSEDED/«[УСТАРЕЛО]»).

## 11. МАСШТАБ (реальные цифры, не «система работает»)

- **Агенты**: 3 основных (gemma, alfa, bravo) + 3 сабагента (delta1/2/3) +
  omega (резерв, без PG) + 3 лёгких (lima/lima1/lima2) + фоновые сабагенты-инструменты
  (RAG-инжестор, vision-OCR).
- **В эксплуатации**: с 22.09.2026 (50 дней до 11.11.2026). Не «непрерывно» — были
  инциденты и отключения света; живость — по heartbeat `lives`, не по отработке.
- **Циклы**: 339 controlled-restart-циклов основных агентов (gemma 25, alfa 205,
  bravo 80, delta1/2 по 14, delta3 1 — счётчик `lives.restart_count`; сумма = 339).
  Лёгкие/фоновые сабагенты считаются отдельно и в сумму не входят.
- **RAG-память**: 2704 карточки в `knowledge_base` (pgvector, BGE-M3 1024d); эмбеддинг
  ~0.04–1 с (GPU), 2-3+ карточки за цикл.
- **Модели**: локальные GGUF (llama.cpp, OpenAI-совместимый API), окно до ~140k,
  completion до 16k. Чистые замеры одного и того же 2×GPU-размещения: llama.cpp ≈ 50 ток/с,
  vLLM (AWQ, tensor-parallel 2) ≈ 86 ток/с. Движки не смешаны — ось сравнения = движок,
  а не железо/ОС (сравнение по железу/ОС — в RAG-карточках, не здесь).
